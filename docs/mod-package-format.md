# Mod package format (P0/P2)

A project, installed mod and unzipped package share this layout:

```text
mods/<id>/mod.json                 runtime identity and dependencies
          package.json            packaging identity, version and file hashes
          data/...                loose overlay, mirroring the game's data/
          src/...                 optional authoring sources; excluded
          out/...                 optional generated outputs; excluded
          .scratch/data/...       local editor overlay; excluded
          .modindex-cache         engine cache; excluded
          .install-receipt.json    installer receipt; excluded
```

The shipped `tools/mc2mod/mc2mod.py` is the CLI. Its `.mc2mod` archives are ZIP
files with relative paths at archive root, without a containing id directory.
This codifies the existing **`mc2-package/1`** schema; the strategy document's
`mc2-mod-package/1` spelling was a proposal, not a second supported format.
The engine reads `mod.json`, never `package.json`. Legacy folders without either
manifest remain runtime-compatible and are never upgraded implicitly.

Minimal `mod.json`:

```json
{"id":"minimal-mod","name":"Minimal mod","version":"1.0.0","dependencies":[]}
```

`package.json` is generated by `pack`:

```json
{
  "schema": "mc2-package/1",
  "id": "minimal-mod",
  "name": "Minimal mod",
  "version": "1.0.0",
  "dependencies": [],
  "files": [
    {"path":"mod.json","size":91,"sha256":"<64 lowercase hex characters>"},
    {"path":"data/example.txt","size":7,"sha256":"<64 lowercase hex characters>"}
  ]
}
```

The example sizes/hashes are illustrative; the fixture has actual values.
Required fields: schema, id, name (string), version, files (nonempty array).
Ids match `[a-z0-9][a-z0-9._-]*` and must equal `mod.json.id`. Versions use the
existing CLI's dotted numeric syntax (one to four components, optional `-` or
`+` suffix). Optional dependencies are ordered `{id, version}` objects; their
ids must exactly mirror `mod.json.dependencies` (strings). `*` is the packer's
default version constraint; constraints are advisory, not resolved by this tool.
Other metadata is ignored; it does not register assets or change runtime behavior.

Each file entry requires a relative forward-slash path, nonnegative integer size
and SHA-256. No absolute paths, parent/dot segments, Windows special characters,
case-insensitive duplicates, `src/`, `out/`, dot-prefixed entries or self-entry
for `package.json`. Every distributed file, including `mod.json`, is listed.
Project-only sources and dotfiles may remain in a project but are not payload.
`--check-files` checks declared sizes/hashes and rejects undeclared payload files
and paths escaping the root. Validation does not interpret FIT, PAK, TGL or FST.

```text
py -3 tools/validate_mod_package.py <mod-folder> [--check-files]
py -3 tools/validate_mod_package.py --legacy-install --check-files <deploy> ...
py -3 tools/mc2mod/mc2mod.py list --deploy <game>
py -3 tools/mc2mod/mc2mod.py check --deploy <game> --active <folder> [--deps a,b] [--log engine.log]
py -3 tools/mc2mod/mc2mod.py rollback <id> --to <version> --deploy <game>
```

Validator exit 0 means no errors, 1 means validation errors. Legacy inventory
prints `LEGACY`, never package `PASS`; missing metadata cannot certify integrity.
`list` is read-only and shows each installed folder, version and receipt presence.

`check` reuses the merged L1 static resolver: scratch > active > declared deps >
additional `--deps`, first wins, with dotfile exclusion and case folding. Only
the selected chain participates; inactive mods do not conflict. It hashes live
bytes, so legacy mods and local edits are included. Same bytes are INFO;
different bytes are WARN. It also warns on shared `class:appearanceName`
(`replaces`) keys across model override manifests. Warnings do not block (exit 0).
It emits the engine's exact `[mod-dup] path  winner=[id]  loser=[id]` lines.
`--log` compares their multisets to a fresh `MC2_LOG_FILE_RESOLVE=1` engine log,
returning 1 for any missing/extra collision. Use the same active mod, dependency
and scratch settings and `MC2_REBUILD_MOD_CACHE=1` when recording the log.
This predicts indexing collisions; subsequent engine-specific stock-AI/kit
filters and asset semantics remain the engine's responsibility.

Upgrades install into private `mods/.staging/`, validate the complete folder,
and rename the old version to `mods/.trash/<id>-<version>-<unique>/` before
activating the new folder. `rollback` selects exactly one retained id/version,
verifies both versions and receipts, and swaps back, retaining the displaced
version. Missing/ambiguous versions, edited payload, shared mutation receipts,
legacy/unmanaged targets and linked directories are refused without replacing
the active folder. A failed activation rename restores the previous folder.
Two renames are recoverable on an ordinary error, not power-loss atomic; concurrent
mutation commands on one deploy are unsupported. Rollback does not repair an
already damaged active version. Archives are retained until explicitly removed.
No tool changes saves or base files. `unset MC2_ACTIVE_MOD` remains vanilla mode.

Compatibility check (2026-10-29): read-only legacy inventory of MC2X-CVE-G,
MC2X-REAP3, MC2-Exodus, MC2-MagicExpansion, MechCommanderOmnitech and MCO-Carver5
under `A:/Games/mc2-opengl/` succeeded. All six lack package metadata; none was
modified or represented as integrity-certified. Their loose data file counts
were 13031, 676, 11221, 12007, 10909 and 1504 respectively.
