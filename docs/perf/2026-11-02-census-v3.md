## Where the time goes (ranked) and the path to 100 fps

1. Main-thread render extraction/submission (main_exec): 4.0 ms at mc2_10 wolfman, 3.9-5.9 ms at scout 4K. About 500 prop draws plus ~490 shadow draws at mc2_10; shadow draws roughly equal prop draws (per-prop shadow pass not instanced). Culling shadow draws or batching them is the biggest CPU lever.
2. GPU time at 4K scout poses: 5-7 ms, and shadow draws jump from ~90 (1080p) to ~530 (4K) there, so shadow cascade work scales with resolution; this is the GPU-bound case. Needs an RGP capture to rank passes.
3. Sim tick with 200 movers: 6.7 ms median, 23.8 ms max, will break 100 fps (10 ms) on tick frames.
4. wait_sealed: a flat ~0.35 ms on every pose (worker handoff), constant floor.
5. extract_render_list walk: 54-129 us per frame, negligible.

Reaching 100 fps: the measured corner-class poses already run 160+ fps at 4K and 300+ at 1080p, so 100 fps is met on mc2_03/mc2_17/mc2_01 and on mc2_10 wolfman. The open risks are (a) mc2_24, which must be re-measured with a valid run and a corner bookmark, and (b) 200-mover ticks. Both require a rerun, not an optimisation, before work is prioritised.


## Follow-up (same day): RGP diagnosis, corner bookmarks, Tracy, answers

The table rows above for mc2_01, mc2_24 and the new corner_far poses are from the follow-up reruns and supersede the first-pass numbers. Corner-far bookmarks were added for mc2_10 and mc2_24 (same geometry as mc2_17: pos -6400,-6400, rot 134.875, proj 14.875, alt 5775.8). wolfman is proj 60 / alt 6000, a steep view, so it is NOT the worst case; the corner pose is. Worst case measured: mc2_24 corner_far 189 fps at 1080p (5.3 ms, 897 prop draws, CPU-bound, main_exec 4.65 ms) and 167 fps at 4K. mc2_10 corner_far: 266-274 fps. All poses exceed 100 fps.

Why verdicts failed (mc2_01 1080p, mc2_24 runs): the runner gate `vegetation_visible_missing` (no `[VEG_GPU]` line with visible survivors >= 100). It is a vegetation-cull gate, not a crash or timeout (exit 0); frame data are complete. It is borderline per run (mc2_01 4K passed). Rows are kept and flagged. mc2_24 did NOT reach the same state at both resolutions: at 4K mech draws are 0 and shadow draws collapse in every run (reproducible), at 1080p mechs draw (82-120). The lance is not drawn at 4K at this point in the mission (cause not diagnosed), so mc2_24 4K rows exclude mech cost; mc2_24 1080p rows are the trustworthy ones.

306 fps vs 225-233 for mc2_10 wolfman: 306 is not reproducible for mc2_10 (it is the mc2_17 corner_far 1080p figure; I likely misattributed it). My other in-progress mc2_10 wolfman readings were 261/253 fps against 225/233 in the sweep: same ts0 setting and build, so the gap is run-to-run spread under shared-machine load (other lanes ran concurrently). Treat any single number as +-15 percent. Not a timestamp effect.

Tracy split (mission_cpu_profile.py, new --pose option, mc2_10 wolfman, 1080p; proofs/census3/tracy/20261102T055137.352542Z/profile.md): per frame (7274 frames) Frame 2.34 ms, DrawScreen 1.11 ms (Camera.UpdateRenderers 1.03; GameCamera::render 1.02; textureManagerRenderLists 0.71), GameLogic 0.99 ms, present 0.006 ms. So draw-list flush (textureManagerRenderLists) is the largest single main-thread block, about 30 percent of the frame. Caveat: this harness runs a frozen-PNG-sweep phase, so its absolute mean (about 427 fps) is faster than the bench rows; use the shares only.
