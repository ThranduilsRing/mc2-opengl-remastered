# Gate reader conflicts

Every gate whose readers answer differently for at least one of the eight probe inputs. A typed gate table gives each gate one truthiness rule, so each row below is a place where that rule would change some reader's behaviour; G0 of the typed-gate-registry design unifies each one, or records it as an owner-decided divergence. Generated by `py -3 tools/gate_conflicts.py --write`; the ratchet is `tools/gate_conflicts.py --check` against `tools/gate_conflicts.baseline.json`.

Probes: **U** unset, **E** `""`, **Z** `"0"`, **F** `"false"`, **O** `"1"`, **X** other (`"yes"`; the sub-probes `"10"` and `"2.5"` separate first-character and prefix-parse readers). Outcomes are oriented so that `"1"` asserts the gate: a reader that uses the variable as a disable flag is shown as the same test, marked *(inverted use)*. `D` in a vector means the reader keeps whatever default it already had; `?` means the answer depends on program state the tool cannot see; `inh` means the reader inherits an umbrella gate. Neither counts as a disagreement.

## Sites the tool could not classify (18)

Mostly string- and path-valued reads whose only use is a library call (`fopen`, `snprintf`). They are listed in the JSON; the ratchet forbids the number rising so a new idiom cannot hide.

## Method and limits

- The reader's C++ is executed, not pattern-matched; the interpreter is `scripts/gate_idioms.py` and shares its source plumbing with `scripts/check-gate-default-agreement.py`.
- A condition on some other piece of program state is treated as the identity of `&&`/`||`: `getenv(X) && frame % 64 == 0` is a presence test as far as X goes.
- Table-driven reads (`kEnvGates[i].name` passed to getenv later) and names built at run time are invisible to a literal scan; they are counted under non-call literals.
- Reads of the same gate in different processes (editor, tools) are compared too; whether two readers can ever coexist in one run is a G0 judgement, not this tool's.
