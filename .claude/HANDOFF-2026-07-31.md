## 7. The cursor fix and the isolation study

### 7.1 `CURSOR-GRAB-FIX-1` (`ffebf5e87`)

*Title: "an invisible window may never capture input".*

An offscreen run — the mode every headless capture uses — was parking the window
at (-32000,-32000) and then **still grabbing the cursor, the keyboard and the
foreground**. The user's cursor was stolen repeatedly during this session; that
is what caused launches to be hard-blocked in the first place.

The mechanism, from the commit message: *"a window that is not visible to the
user must never capture the user's input — no grab, no clip, no warp, no
foreground activation — and it must stay that way across focus events."*

| Piece | Where |
|---|---|
| The single policy predicate `gos_CursorCaptureForbidden()` | `GameOS/gameos/gameos_input.cpp:116` — declared `gos_render.h:33-51` |
| Keyed on **intent** (`MC2_NO_CURSOR_GRAB` / `MC2_SMOKE_MODE` / `MC2_WINDOW_OFFSCREEN`) **and actual visibility** (not hidden/minimised, non-degenerate, intersects a display) | `gameos_input.cpp:77-129` |
| The chokepoint all seven arm paths funnel through | `apply_mouse_grab()`, `gos_render.cpp:48`; guard at `:69` |
| **Geometry failsafe — independent of every env gate:** `ClipCursor` refused outright when the rect lands on no monitor | `gos_render.cpp:139-146` (`MonitorFromRect`/`MONITOR_DEFAULTTONULL`) |
| `WS_EX_NOACTIVATE \| WS_EX_TOOLWINDOW` applied **before** the window is ever mapped | `gos_render.cpp:254`, applied `:551`, before `SDL_ShowWindow` at `:552` |
| Crash-bundle `HWND_TOPMOST` modal dialog suppressed on unattended runs | `gos_crashbundle.cpp:516-521` |
| Contract checker — 5 assertion families, 19 watched API tokens across 11 engine dirs | `scripts/check-input-capture-visibility.py`, wired at `scripts/check-contracts.sh:360-361` |

Two design choices worth knowing: the `SDL_WINDOWEVENT_FOCUS_GAINED` re-arm at
`gameosmain.cpp:555-565` is **deliberately left unconditional** ("Do not add a
second copy of the policy here") — it is defeated because `apply_mouse_grab`
re-evaluates the predicate on *every* call. And `gos_WindowUserVisible`
**fails open**: if displays cannot be enumerated it returns visible, so an SDL
hiccup never disables the grab for a real player.

**Normal launch is unchanged — verified from source.** With none of the three
env vars set and a visible window, the predicate falls through all four arms and
`ClipCursor` still runs. The cursor is still confined to the game window, which
is correct for a game someone is playing.

**Status: UNVERIFIED AT RUNTIME, and unverifiable from any install on disk.**
`ffebf5e87` is not an ancestor of any of the four deployed fingerprints
(checked with `git merge-base --is-ancestor` against all four). The new
`[CURSOR_GUARD]` marker string appears in **zero** log files anywhere in the
tree — if the fixed binary had ever run unattended it would have printed one.
**A rebuild and deploy is a precondition for the check below.**

**The four-step supervised check, in order** (against a build containing
`ffebf5e87`):

1. **Normal launch.** Cursor still confined to the game window. *This is
   correct* — the fix must not change normal play.
2. **`MC2_WINDOW_OFFSCREEN=1` alone.** Cursor free across the whole desktop for
   the **entire** run — **including after clicking another window**. That last
   clause is the real test; the old failure re-armed on `FOCUS_GAINED`.
3. **No taskbar button, no Alt-Tab entry, no keystroke leakage** into whatever
   has focus.
4. **Offscreen capture still produces real pixels**, not black. A fix that buys
   safety by breaking capture is not a fix.

> **⚠ Trap in step 2 — do not use `run-with-log.bat`.** That file now contains
> `if defined MC2_WINDOW_OFFSCREEN set MC2_NO_CURSOR_GRAB=1`
> (`run-with-log.bat:16`). Running step 2 through it would free the cursor via
> the *old* `MC2_NO_CURSOR_GRAB` arm and never exercise the new
> `MC2_WINDOW_OFFSCREEN` arm at all — **a false pass.** Set the variable
> directly and invoke the exe.

**Three residual gaps in the fix**, found in review and not yet addressed:
`WS_EX_APPWINDOW` is only ORed, never cleared (contrast

### 7.2 Launch isolation — none of the assessed mechanisms proved safe

`.claude/LAUNCH-ISOLATION-VALIDATION.md` (`c09234f6f`, 446 lines) assessed the
candidate mechanisms for letting an agent launch the game without touching the
user's desktop. **None was proven safe. The block stays.**

| Mechanism | Verdict (verbatim) |
|---|---|
| Job objects + `CREATE_NO_WINDOW`/`DETACHED_PROCESS` | **REFUTED — structurally, cannot be fixed** |
| Offscreen / hidden window (`MC2_WINDOW_OFFSCREEN`) | **REFUTED — was never a boundary, and is currently armed** |
| Private window station + desktop | **REFUTED — cooperative, not enforced** |
| VM / second session / RDP-to-self | **REFUTED — measured absent or actively disruptive** |
| Session 0 (S4U scheduled task) | **NOT REFUTED — and NOT PROVEN** |

**The private-window-station escape was reproduced, in four unprivileged
calls** — verified against the on-disk probe artifact:

```
OpenWindowStationW("WinSta0", WINSTA_ALL_ACCESS)  ->  SetProcessWindowStation
  ->  OpenDesktopW("Default")                     ->  SetThreadDesktop
```

*"The process started isolated and ended on `WinSta0\Default`. Same user, same
token; `WinSta0`'s DACL grants the interactive logon session and nothing revokes
it. Four ordinary calls, no admin."* The prior lane's cited proof of the
opposite is dismissed as a tautology: `OpenDesktopW("Default")` from inside the
private station was *guaranteed* to fail because desktop names resolve relative
to the caller's current window station — the decisive call,
`OpenWindowStationW("WinSta0")`, had never been made.

**Session 0 is the only candidate still standing**, and the study is explicit
that it is unproven rather than safe: the specific escape that killed the
private-window-station mechanism has never been measured against session 0.
That single measurement is the gap between "keep the block" and "here is a
mechanism", and the study deliberately did not take it — *"a scheduled task is
persistent machine configuration and that is your decision, not an agent's."*

**Two caveats the study makes about its own evidence, which matter:**

- **The engine was never launched.** Not once, in any lane. Every measurement
  came from throwaway probe processes plus `SDL2.dll` loaded as a library.
- **The locked-workstation confound.** Every run in the entire body of work
  happened with the workstation locked, so every "the supervisor saw no change
  to foreground or cursor" result is a **null instrument** — it was comparing
  `None` to `None`. That evidence carries no information and must not be read as
  reassurance.

The study's own recommendation, followed 37 minutes later by `ffebf5e87`, was to
fix the offscreen cursor defect independently: *"Cost: near zero. Recommended
regardless of what you decide about isolation. It removes a live trap, and it
does not lift or weaken the block in any way."*

## 10. The hard-won rules

These cost real time today. Each is here because a lane learned it the
expensive way.

1. **Read gate defaults from the C++ reader, not from docs, commit messages, or
   the registry doc string.** The registry's `defaultOn` field and the actual
   `getenv` idiom have drifted more than once. `MC2_TERRAIN_AMBIENT_FLOOR` was
   reported as default-OFF by a checker purely because a *debug trace* line
   contained a bare `getenv` with no idiom attached
   (`gos_terrain_lod_chunk.cpp:2880-2883`). `scripts/build_review_pack.py`
   deliberately refuses to store defaults in its manifest and re-resolves them
   from source at render time for exactly this reason.

2. **Prove a check fires by injecting the real regression into the live tree.**
   A checker that has only ever seen the fixed tree is a checker that has never
   been tested. Positive control *and* negative control, both directions — the
   ledger's Dispute 3 is the model: the same tool reported `dirty: false` on a
   clean exe and `dirty: true` on a dirty one, so the scan is not one that
   always says "clean".

3. **A pathspec commit takes the whole working-tree file.** In a shared worktree
   with parallel lanes, `git commit <path>` will sweep in another lane's
   uncommitted edits to that path. **Use a private index:**
   ```sh
   export GIT_INDEX_FILE=<scratch>/my.index
   git read-tree HEAD
   git add <paths>
   git diff --cached          # READ THIS
   git commit -m "..."
   git show --stat HEAD       # verify: only your files
   ```
   Cost: the shared index is now littered with stale pre-commit snapshots (§2).
   That is the acceptable price; a blanket `git reset` would destroy another
   lane's staged work.

4. **`git apply --unidiff-zero` can silently misplace a pure-insertion hunk.**
   With zero context lines there is nothing to anchor on, so the hunk lands at
   the stated line number whether or not that is still the right place. Verify
   the result, do not trust the exit code.

5. **A background build can report exit 0 while the link failed.** Check the
   artifact, not the status. And check the *fingerprint* of the artifact —
   `scripts/exe_fingerprint.py` against the exe — not the generated header,
   which only records what cmake last stamped.

6. **THE RECURRING ROOT FAILURE — a lane measures a number, reports it, and
   never commits the artifact.** The next lane greps the repo, finds nothing,
   and grades the number fabricated. **Both lanes behaved correctly.** The repo
   is not a record of what was measured; it is a record of what was
   *committed*.

   This happened at least four separate times today, and it is why
   `.claude/MEASUREMENT-LEDGER.md` exists. Before writing "fabricated", check:
   untracked files (`git status --porcelain`, leading `??`), sibling worktrees,
   sibling *installs*, commits that **pruned** an artifact after it was used
   (`git log --diff-filter=D`), and `git log --all --oneline -- <path>` — a file
   can be `??` in your worktree and committed on a ref you are not on.

   **The fix is one `git add`.** Do it in the same commit as the claim.

7. **Corollary — say which route produced a number.** "Verified from the exe" and
   "verified from the manifest" are different strengths of claim and get
   different verdicts. Naming the route is the difference between a number that
   survives adjudication and one that gets retracted.
