### 6.5 A failing row could not say why

`run_check_tri` **captured a failing row's output and then discarded it** under
`--quiet` — the mode everybody runs — so the one row structurally able to explain
itself rendered as a bare `FAIL`. Fixed in `8b3e040bb`.

**It did not generalise by reuse, and it has now landed properly.** `run_check_tri`
has exactly **one** invocation (`capture_provenance`); the other 142 rows go through
`run_check`, which under `--quiet` ran `eval "$cmd" > /dev/null 2>&1` (`:135`) and
**never captured output at all**. Generalising therefore required *restructuring*
`run_check`, not reusing the tri patch — which is what lane `FAIL-REASON-1` did, in
**`25008e321`**, landed while this handoff was being written.

Two properties of that fix worth carrying, because they are what makes it safe:
**a passing row still prints nothing** under `--quiet`, so a green board is
byte-for-byte as quiet as before and added output is proportional to *red* rows
only; and a chatty failure is **windowed** (head 8 + tail 32). Burying the one real
red row under a noisy one is the failure mode of a fix like this, and it is
prevented structurally rather than by good manners.

Its commit also names the reason the discard survived so long, which is the more
transferable finding: `--quiet` dates from when the board had **eight** rows, where
"re-run without `--quiet`" cost seconds. At **143** rows and ~340 s it costs six
minutes, so nobody did it — and **a red row with no reason becomes wallpaper.**
That is precisely how `capture_provenance` sat untouched as "known-red, not mine"
while three of its five findings were user decisions and two were already pinned.

### 6.7 An amber acknowledgement can sit forever

`MAX_ACK_DAYS = 365` (`scripts/check-capture-provenance.py:190`), but the comparison
at `:645` is

```python
elif exp_d is not None and exp_d > today + datetime.timedelta(days=MAX_ACK_DAYS):
```

where `today` is the **run date** (`:611`). So the cap bounds how far into the future
an entry may claim to expire *as of whenever you happen to run the check* — it never
references when the entry was **acknowledged**. Editing `expires_utc` forward once a

The field that would catch exactly that, `acknowledged_utc`, is **written on every
entry and read by nothing** — `scripts/provenance-known-failures.json:49,:59` write
it; a repo-wide grep finds no reader. The checker's own comment at `:177` says so:
*"read by NOTHING in this file -- grep it."* Documented limitation, not a bug report;
closing it is a small, well-specified slice.

### 6.8 Found while doing this handoff: the review-pack generator degrades silently

`scripts/build_review_pack.py` rebuilds the user-facing **gate inventory** by parsing
`RenderCore/RendererFeatureRegistry.h` at render time — deliberately, so published
defaults cannot drift from compiled ones (§11.1). If that parse fails it prints a
**stderr WARNING and continues** (`parse_registry`, `:95-99`), and the file is opened
with `errors="replace"`, so a truncated or mid-write header never raises.

**I hit it.** My first regeneration tonight produced a page with **10 gate entries**
and the message `WARNING: table kAuxEnvVars not found`. Three subsequent runs produce
**359 entries**, no warning, byte-identical output. `RendererFeatureRegistry.h` is not
dirty and HEAD did not move, so the most likely cause is a **transient read while a
concurrent lane had the header open for writing** — the same hazard as §11.6, in a
different file.

**Severity is the point, not the frequency.** That run exited **0** and wrote a
perfectly well-formed page whose gate inventory was **97 % empty**. Nothing failed,
nothing was red, and the user would have been reading a table with 349 gates missing.
*Observed once; the mechanism is verified from source; I could not reproduce it on
demand.* The fix is small — make the missing-table case a non-zero exit, or assert a
floor on the parsed entry count — and is **not** in this lane's scope.

## 7. The cursor fix and the isolation study

### 7.1 `CURSOR-GRAB-FIX-1` (`ffebf5e87`) — *"an invisible window may never capture input"*

An offscreen run — the mode every headless capture uses — was parking the window at
(-32000,-32000) and then **still grabbing the cursor, the keyboard and the
foreground**. The user's cursor was stolen five times; that is why launches are
hard-blocked.

| Piece | Where |
|---|---|
| Policy predicate `gos_CursorCaptureForbidden()` | `GameOS/gameos/gameos_input.cpp:116`, declared `gos_render.h:33-51` |
| Keyed on **intent** (`MC2_NO_CURSOR_GRAB` / `MC2_SMOKE_MODE` / `MC2_WINDOW_OFFSCREEN`) **and actual visibility** | `gameos_input.cpp:77-129` |
| Chokepoint all seven arm paths funnel through | `apply_mouse_grab()`, `gos_render.cpp:48`; guard `:69` |
| **Geometry failsafe, independent of every env gate:** `ClipCursor` refused when the rect lands on no monitor | `gos_render.cpp:139-146` |
| `WS_EX_NOACTIVATE \| WS_EX_TOOLWINDOW` applied **before** the window is mapped | `gos_render.cpp:254`, applied `:551`, before `SDL_ShowWindow` `:552` |
| Contract checker — 5 assertion families, 19 watched API tokens, 11 engine dirs | `scripts/check-input-capture-visibility.py` |

**Normal launch is unchanged — verified from source.** With none of the three env
vars set and a visible window, the predicate falls through all four arms and
`ClipCursor` still runs. The cursor stays confined to the game window, which is
correct for a game someone is playing. The visibility test **fails open**: if
displays cannot be enumerated it answers "visible", so an SDL hiccup never disables
the grab for a real player — and that arm cannot weaken the offscreen check, because
`MC2_WINDOW_OFFSCREEN` is matched *before* visibility is consulted.

**Status: present in a binary, never observed.** `ffebf5e87` is in CURSORFIX
(§3). The `[CURSOR_GUARD]` marker appears in **zero** log files anywhere — if the
fixed binary had ever run unattended it would have printed one.

**The four-step supervised check, in order** (on CURSORFIX):

1. **`CURSOR-1-normal-launch.bat`** — plain launch. Cursor **still confined** to the
   game window. *This is correct.* If it roams here, the guard went too far. This is
   also the smoke test: **nobody has confirmed this executable even starts.**
2. **`CURSOR-2-offscreen-alone.bat`** — `MC2_WINDOW_OFFSCREEN=1` alone. Cursor free
   across the whole desktop **for the entire run, including after you click another
   window.** That last clause is the real test — the old failure re-armed the grab on
   the first `FOCUS_GAINED` event, so a check that looked only at the first second
   would have passed *before* the fix too.
3. While step 2 runs: **no taskbar button, no Alt-Tab entry, no keystroke leakage.**
4. **An offscreen capture still produces real pixels, not black.** A fix that buys
   safety by breaking capture is not a fix.

> **⚠ Two ways to score this wrong.**
> **(a) Scoring a non-event as a pass.** An offscreen run shows nothing — no window,
> no taskbar entry. That is indistinguishable from *the engine having died two
> seconds in*, in which case your cursor is also free, for the wrong reason. **No
> `[CURSOR_GUARD]` line in the console ⇒ the check did not happen.** Step 4 is what
> converts a non-event into evidence.
> **(b) Running step 2 through `run-with-log.bat`.** Line 18 of that file sets
> `MC2_NO_CURSOR_GRAB=1` whenever `MC2_WINDOW_OFFSCREEN` is defined — correct for an
> interactive launcher, but it would free the cursor via the **old** arm and never
> exercise the new one. **A false pass.** `CURSOR-2-offscreen-alone.bat` invokes the
> executable directly and deletes both `MC2_NO_CURSOR_GRAB` and `MC2_SMOKE_MODE`
> first, so neither a leftover shell variable nor `launcher_env.json` can manufacture
> a pass. Step 3 also means you **cannot close it normally** — open Task Manager
> before you launch.

**Residual gaps, named by the fix's own author and not closed:**
`WS_EX_APPWINDOW` is only ORed, never cleared (contrast `editor/EditorGosRender.cpp:283`,
which clears it) — if SDL ever sets it, it overrides the taskbar suppression;
`SDL_ShowCursor` (`gos_render.cpp:569/571`) is unguarded and absent from the
checker's token list; the live-tree injection proof was taken 18 minutes before the
final window-styles edit (mutated regions byte-identical, so coverage holds, but the
proof is not against the committed file); SDL's grab/hint behaviour was read as
**documentation, not source**; driver overlays and in-process shims can take the
pointer outside this guard entirely; and **the Mission Editor is not covered** — it
has its own window code and no reference to `gos_CursorCaptureForbidden`.

### 7.2 Launch isolation — none of the mechanisms proved safe

`.claude/LAUNCH-ISOLATION-VALIDATION.md` (`c09234f6f`, 446 lines). **None proven
safe. The block stays.**

| Mechanism | Verdict |
|---|---|
| Job objects + `CREATE_NO_WINDOW`/`DETACHED_PROCESS` | **REFUTED — structurally, cannot be fixed** |
| Offscreen / hidden window | **REFUTED — was never a boundary** |
| Private window station + desktop | **REFUTED — cooperative, not enforced** |
| VM / second session / RDP-to-self | **REFUTED — measured absent or actively disruptive** |
| Session 0 (S4U scheduled task) | **NOT REFUTED — and NOT PROVEN** |

The private-window-station escape was **reproduced in four unprivileged calls**:
`OpenWindowStationW("WinSta0", WINSTA_ALL_ACCESS)` → `SetProcessWindowStation` →
`OpenDesktopW("Default")` → `SetThreadDesktop`. The prior lane's proof of the
opposite was a tautology — `OpenDesktopW("Default")` from *inside* the private
station was guaranteed to fail, because desktop names resolve relative to the
caller's current window station. The decisive call had never been made.

**Two caveats the study makes about its own evidence:**

- **The engine was never launched.** Not once, in any lane. Every measurement came
  from throwaway probe processes plus `SDL2.dll` loaded as a library.
- **The locked-workstation confound.** Every run happened with the workstation
  locked, so every "the supervisor saw no change to foreground or cursor" result is
  a **null instrument** — comparing `None` to `None`. **That evidence carries no
  information and must not be read as reassurance.**

Session 0 is the only candidate standing, and the study deliberately did **not** take
the one measurement that would settle it: *"a scheduled task is persistent machine
configuration and that is your decision, not an agent's."*

1. **Read gate defaults from the C++ reader** — not docs, not commit messages, not
   the registry's `defaultOn` field. `MC2_TERRAIN_AMBIENT_FLOOR` was reported
   default-OFF by a checker purely because a *debug trace* line contained a bare
   `getenv` with no idiom attached. `scripts/build_review_pack.py` deliberately
   refuses to store defaults in its manifest and re-resolves them from source at
   render time for exactly this reason.

2. **Prove a check fires by injecting the real regression into the live tree.** A
   checker that has only ever seen the fixed tree has never been tested. Positive
   **and** negative control, both directions. The model is the ledger's Dispute 3:
   the same tool reported `dirty: false` on a clean image and `dirty: true` on a
   dirty one, so the scan is not one that always says "clean". §6 is what happens
   without this — five checks lying at once, and 631 tests that no gate ever ran.

3. **Use a private index in a shared worktree — `read-tree` immediately before you
   add, and `git reset` after.**
   ```sh
   export GIT_INDEX_FILE=<scratch>/my.index
   git read-tree HEAD         # RIGHT BEFORE the add, not once per session
   git add <paths>
   git diff --cached          # READ THIS
   git commit -m "..."
   unset GIT_INDEX_FILE && git reset
   git show --stat HEAD       # verify: only your files
   ```
   A pathspec commit takes the whole working-tree file and will sweep in another
   lane's uncommitted edits. But the private index has its own trap, and this lane
   nearly hit it: **your index holds a full tree snapshot, so if HEAD advances after
   your `read-tree`, committing that index silently reverts every file the other
   lane changed** — and `git show --stat` will look innocent, because it only lists
   files that differ from the *new* parent. Re-`read-tree` immediately before
   staging, and check the blob of anything a concurrent lane is touching.

   The previous revision of this file called the resulting shared-index litter "the
   acceptable price". **It is not** — it cost the next lane a diagnosis. Clean up
   after yourself.

4. **`git apply --unidiff-zero` can silently misplace a pure-insertion hunk.** With
   zero context there is nothing to anchor on, so the hunk lands at the stated line
   number whether or not that is still the right place. **Verify the result; the exit
   code means nothing.**

5. **A background build can report exit 0 while the link failed.** Check the
   artifact, not the status — and check the *fingerprint* of the artifact, not the
   generated header, which only records what cmake last stamped.

6. **Do not edit a shell script while it is running.** `bash` re-reads a running
   script by byte offset, so an edit mid-run makes it execute garbage. This produced
   spurious syntax errors twice in one night and probably explains several "races"
   diagnosed as something else. Applies to `scripts/check-contracts.sh` above all —
   coordinate, or wait.

7. **Say which route produced a number.** "Verified from the exe" and "verified from
   the manifest" are different strengths of claim and get different verdicts. Naming
   the route is the difference between a number that survives adjudication and one
   that gets retracted. Corollary: **a retraction needs the same standard of proof as
   a claim.** "I found a number with the same digits" is not a derivation — do the
   arithmetic and check it lands on the number before publishing provenance. An
   unnecessary retraction destroys a true result and costs the reader's trust in
   every other correction on the page.

8. **THE ROOT FAILURE — a lane measures a number, reports it, never commits the
   artifact, and the next lane grades it fabricated. Both lanes behaved correctly.**
   The repo is not a record of what was measured; it is a record of what was
   *committed*. This happened at least five separate times today, and it is why
   `.claude/MEASUREMENT-LEDGER.md` exists.

   Before writing "fabricated", check: untracked files (`git status --porcelain`, a
   leading `??`), sibling worktrees, sibling *installs*, commits that **pruned** an
   artifact after it was used (`git log --diff-filter=D`), and
   `git log --all --oneline -- <path>` — a file can be `??` in your worktree and
   committed on a ref you are not on.

   **The fix is one `git add`, in the same commit as the claim.** It caught itself
   live *again* tonight: `116854` — the assertion count that is the entire evidence
   for §6.3 — existed in **no file in the repo**, tracked or untracked, until this
   handoff pasted the verbatim run into §6.3.
