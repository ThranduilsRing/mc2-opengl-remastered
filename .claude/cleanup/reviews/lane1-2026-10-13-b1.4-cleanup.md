## Findings (by severity)
**M1 (medium, owner ruling). `MissionBegin::updateSplash` swallows the campaign-start pre-video; it is a regression, not an original quirk.** Before d0309b1e6 (2026-10-10, "update as an orchestrator over 7 verbatim phase helpers") the RESTART branch of
`MissionBegin::update()` ended `return LogisticsData::instance->getCurrentBigVideo();` in a `const char*` function, and `Logistics::update` (logistics.cpp:399-402) did `playFullScreenVideo(pVid)`. The extraction made the helper a `bool`, so the same
statement now converts the name to true and `update()` (`if (updateSplash()) return NULL;`, missionbegin.cpp:1671; every other path also returns NULL) discards it. Exact behaviour now, on a campaign start from the main menu (RESTART): the first screen
is `begin()`ed (the common trailing `screens[..]->begin()` is skipped by the early return), `getCurrentBigVideo()` hands out the group's `PreVideo` once and sets `bigVideoShown = true`, the helper returns `!name.empty()`, `update()` returns NULL
for that frame (screen update, tutorial animation and soak walk skipped for one frame) and the movie is never played; stock group 0 has `cinema1.bik` (boot log: `missionbegin: campaign-start pre-video: cinema1.bik`). Because the flag is set, the
after-a-won-mission site (logistics.cpp:346-356) will not offer it later either. `pVid` in `Logistics::update` is dead. `playFullScreenVideo` is a `Logistics` member that returns early for `MC2_BOOT_TO_BAY`, which is why no headless proof ever saw it.
Rulings: (A) keep (no intro movie at campaign start) and delete the dead `pVid` branch and the movie-name plumbing; (B) restore the pre-10-Oct behaviour: `updateSplash` stores the name in a `MissionBegin` member and `update()` returns its `c_str()`
(a movie plays after the first frame of the first screen, as before). B1.4a preserved today's behaviour exactly except for a present-empty `PreVideo = ""` (none in stock data). The comment at missionbegin.cpp:810 calls this "the function answers whether the
splash is still running": wrong on both counts (it answers "a pre-video was pending"); rewrite it after the ruling.
