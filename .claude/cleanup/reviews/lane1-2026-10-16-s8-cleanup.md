## Should-fix
1. Proof gap: B5.5a (5ed477ac9, 13020d572) has no saveload proof of its own. The baselines were recorded at exe d7c8db5a16f2 (before B5.5a). The only later run is the 0ec18e62a re-record at exe e6134a43525a, which does include B5.5a. There the mc2_01/03/16 digests are unchanged, so B5.5a did not move saved bytes on those. mc2_10 and mc2_24 moved, and the commit attributes that to the new WeaponBoltData noise mask; that mask also means the bolt run cannot show a B5.5a change. State this in lane1-state (B5.5a evidence = mc2_01/03/16 digests unchanged at e6134a43525a), and keep "campaign round trip not proven" as an open item until the bisect closes.
2. Latent, pre-existing, now more visible: MechAppearanceData::nodeUsed is long[10] and nodeRecycle is float[10] (mech3d.h:298-299), but copyTo and copyFrom copy 10 BYTES, not 10 elements. For a mech with 3+ weapon nodes only the first 2 longs and 2 floats of the stagger and recycle tables survive a save and load. The commit message ("saved bytes unchanged for 3+ nodes") is correct, but the min() reads as if it fixes the copy, and it does not. Do not fix it in a cleanup lane: it changes saved bytes and post-load sim behaviour and needs a baseline re-record. Record it in docs/known_issues.md or the b5 notes as a save-format bug.

## Nits
- The min(10, size) copy differs from the old code in two cases, both benign. (a) Tables of 1 or 2 nodes: the old code over-read the heap block, so saved bytes 4..9 or 8..9 were heap garbage; they now keep whatever the target already held (uninitialized if MechData is not zeroed first, but no worse than before). (b) 0 weapon nodes: the old code did memcpy of 10 bytes from nullptr; the new code copies 0. Add a WHY comment on the min(): a table smaller than the 10-byte save slot must not be over-read.
- mech3d.cpp: `#include <algorithm>` was added inside the `#ifndef MECH3D_H` guard, so it is skipped whenever the guard is already defined. Move it out of the guard.
- init() in bdactor, gvactor and mech3d: the `nodeUsed = nullptr` resets were removed, so a second init() with numWeaponNodes == 0 would keep stale vector contents. Init runs on fresh objects, so this is harmless.
- bdactor.h, gvactor.h, mech3d.h: the vector declarations keep the old pointer-line alignment padding (a leading space and tab remain on the Bldg and GV lines). Tidy.
- bdactor_update.cpp and gvactor_update.cpp: the loops still run to appearType->numWeaponNodes while the guard is `!empty()`. Equivalent, but nodeRecycle.size() would remove the coupling. Optional.
- 0ec18e62a message says mc2_01/03/16 digests are unchanged. True, but the mc2_01 diff does show a run class label change from data to WeaponBoltData. Say "labels only".
- retiredTypes grows by one per forced reload with no cap. It is bounded by reloads per mission and freed in destroy(), so acceptable.

- Fingerprint (d7c8db5a1): the .beauty sidecars are directories (data/missions/*.beauty), and the walk drops directories ending in .beauty, so they are really excluded. The overlay is hashed by content (sha256); the stock part is archive content plus loose-tree path and size. The digest is deterministic: sorted entries, no timestamps. The selftest covers a changed overlay, a missing overlay, a stray loose file, and a sidecar change not moving the digest. A dirty install is refused by `sim_determinism write-baseline` and by `saveload_roundtrip baseline`. `check` fails on the digest mismatch and adds the problems text. A dirty install cannot match a baseline silently, because the digest covers actual stock and overlay content. Limits, acceptable for the stated purpose: stock loose files are still hashed by size only (a same-size edit outside the overlay goes unseen, as before), and `write-overlay` blesses whatever .fit and .pak files the install holds, with no review step.
- saveload check: a baseline with no data_fingerprint is accepted without a data check (`if bd and cd`). All five were re-recorded with it, so this does not apply today.
