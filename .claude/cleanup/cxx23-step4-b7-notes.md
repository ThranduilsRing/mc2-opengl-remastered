## 4. Conversion rules (G-series; paste into the lane brief)
- G1 **Owner model for actors: seal first, then an owner beside the legacy view.** Two steps, two batches.
  Step 1 (B7o.2, no ownership change): ALL writers of `GameObject::appearance` go through `GameObject::adoptAppearance(Appearance*)` / `releaseAppearance()` (still raw `delete`, same position and order). Writers sealed (the full list, from the census): artlry 677/1527/1593/1661/1729; bldng 1162/1263 and `bldng.h:153` (ctor); `gameobj.cpp` 1515 (`init`) and 1564 (`GameObject::set` copy); gate 657/702; gvehicl 695/1081; mech 519 and `mech_init.cpp` 164; mover 582 and `mover_init.cpp` 413; terrobj 1109/1171/1199 and `terrobj.h:158` (ctor); turret 338/2091/2137. `GameObject::set` and `Mover::set(Mover copy)` stop copying the pointer (a copy NEVER shares an owner; the view is left null in the destination, documented), or are deleted if the call-site grep confirms no caller. `appearance` becomes a `protected`-style member written only inside `gameobj.cpp` (readers keep it: 587 sites unchanged, the F7 pattern).
  Step 2 (B7o.3): the API's body becomes `std::unique_ptr<Appearance> appearanceOwner` (reset-and-replace frees the previous one: the five replacement paths are fixed for free; the former B7.1b/B7.1c are merged because adopting every `new` site already changes replacement cleanup) plus the raw view. Copy constructor: `GameObject` is not copyable once it holds a `unique_ptr`; the by-value `set(copy)` parameter is replaced by `const&` (or the API deleted, step 1). A `static_assert(sizeof(std::unique_ptr<Appearance>) == sizeof(Appearance*))` pins the default deleter. Divergence guard: a debug check in `releaseAppearance`/the destructor that `appearance == appearanceOwner.get()` logs one line (no assert, G12).
- G2 **Lifecycle stays `destroy()`-driven; release at the SAME position.** `Mech` retires its RenderWorld handle before the appearance goes, in destroy AND in the replacement path (`mech_init.cpp:150-164`); `Mover::destroy` frees the appearance before the contacts (`mover.cpp:574-581`); `TerrainObject::destroy` frees its buffers first (`terrobj.cpp:1083`, sub-areas before the appearance); `Artillery::destroy` kills its effects before releasing appearance and bomber (`artlry.cpp:1493`). Building/Gate/Turret/GroundVehicle are plain. Building and tree destructors invalidate their static-prop registrations before the shapes (`bdactor_static.cpp:716`); no owner callback was found, none is added. `releaseAppearance()` replaces `delete appearance; appearance = nullptr` at each site WITHOUT moving it. A doctest records the order of events (handle retire, appearance destructor count, contacts) per class.
- G3 **Backstop (corrected rev 2).** Pool deletion already runs the derived destructors, which call `destroy()` (`mech.h:716`, `objmgr.cpp:943`); therefore the `unique_ptr` destructor is a pure backstop that should find the owner already empty. The teardown order is fixed by `Mission::destroy`: actors first (`mission.cpp:1036`), appearance types after (`mission.cpp:1089`), `SensorManager` between objects and teams (`mission.cpp:1064`); editor objects are cleared before the editor registry. Doctest pins: derived destructor count == object count, `Appearance::destroy` count per instance == 1, and a REPEATED teardown (destroy twice) frees nothing twice.
- G4 **Zero-fill stays, rationale corrected.** `GameObject::operator new` memsets because (a) saves copy whole member arrays and heap garbage would make the save a function of history, AND (b) conditional initialisation: when `initialize == false`, `Mover::init` skips the `appearance`/`contactInfo` assignments (`mover_init.cpp:409-420`) yet destruction reads those pointers, so a zeroed pointer is the only safe default. `std::make_unique<T>()` is NOT a replacement and is not the point: it still invokes the class `operator new` (so the memset would survive), but it value-initialises nothing a constructor skips; the plan keeps the operator pair and the pooled `operator new` call sites unchanged. A pre-construction memset is compatible with a `unique_ptr` member constructed afterwards (the member's constructor writes null over zero); no whole-object self-memcpy exists in the tree. Poisoned-heap doctest (H5) allocates a derived object and reads every byte.
- G5 **Waypoint markers: separate WIRE records from RUNTIME owners.** Today `QueuedTacOrder` (`warrior.h:651`) holds the raw `marker` pointer and the whole struct is `MemCpy`'d into `MechWarriorData` on save (`warrior_state.cpp:610`, then nulled in the staging copy at 613) and back on restore (`:733`, then nulled and rebuilt at 738-749 from `moveMode`). The shift in `removeQueuedTacOrder` (`warrior_queue.cpp:80`, `tacOrderQueue[i] = tacOrderQueue[i+1]`) also copies the pointer. A `unique_ptr` INSIDE `QueuedTacOrder` would duplicate ownership on every one of these copies and the staging nulling would delete the live marker.
  Rule: `QueuedTacOrder` is the WIRE record, UNCHANGED (layout pinned by `save_layout_guard.h`; the `marker` field stays, is always null on the wire and in the queue, and is documented as dead storage). The owners are a new member `std::array<std::unique_ptr<BldgAppearance>, MAX_QUEUED_TACORDERS_PER_WARRIOR> queueMarkers` of `MechWarrior`, index-parallel to the queue. Waypoint storage is a fixed inline array (`warrior.h:759`) plus the global static `TacOrderQueue[]` (`warrior.cpp:291`); neither destructs elements, so the explicit resets below are mandatory, not left to destructors.
  Flows: (1) enqueue: `queueMarkers[n] = adopt(getWayPointMarker(...))` (the factory returns `unique_ptr`). (2) dequeue/shift: `queueMarkers[0].reset()` (deliberate delete, replaces `delete ...marker`), the record shift stays a plain record copy, the markers shift by `std::move(queueMarkers[i+1])` for i in [0,n) so each live marker has exactly one slot and the vacated tail is null. (3) clear: `reset()` over all slots (replaces the delete loop). (4) SAVE: `MemCpy(data.tacOrderQueue, tacOrderQueue)` copies records only (no owners are touched); the per-slot nulling of the staged `marker` field becomes a no-op kept for safety; `queueMarkers` is never read by the save writer. (5) RESTORE: copy the wire records in, then for each slot FIRST `queueMarkers[i].reset()` (the previous run's marker, owned and released exactly once), then rebuild only for `i < numTacOrdersQueued` from `moveMode` exactly as today; empty slots stay null. (6) destroy of the warrior: reset all. No transfer ever copies a `unique_ptr`; no staging copy ever holds an owner.
- G6 **ObjectType.** `ObjectTypeManager` already owns types by `unique_ptr` (`typeStore`, `retiredTypes`). `ObjectType::inUse()` means `numUsers > 0` and `operator delete` checks it AFTER destruction (`objtype.cpp:94`, `objtype.h:111`), so "withhold the free" never made an in-use type valid. REV 2: the forced-reload RETIREMENT (the s7 mechanism: an in-use type moves to `retiredTypes` instead of being destroyed) STAYS exactly as is, and ordinary removal of a zero-user, non-lovable type stays permitted. B7o changes ONLY the allocator behind the operator pair (B7o.9), never the retirement or the guard; any "explicit rule" is a comment beside `retiredTypes`, not a behaviour change.
- G7 **objTypeManager keeps a raw VIEW and gains an owner.** `GameObjectManager::objTypeManager` stays `ObjectTypeManager*` (tests assign borrowed objects, `test_part_archive.cpp:112`); a new `std::unique_ptr<ObjectTypeManager> ownedTypeManager` is what `init` fills and `destroy` resets. Owner-plus-view is two pointer members instead of one (accepted: no test edits). Both are kept in sync explicitly, INCLUDING the parameterless `init()` that nulls the view (`objmgr.cpp:112`).
- G8 **Ended artillery round.** RETENTION CONFIRMED by the review: ending a round disables it via `MC2_DESTROY` (`objmgr_update.cpp:1362`), rendering requires `getExists()`, and re-use destroys the retained resources (`objmgr.cpp:1247`), so retention is bounded by pool size; the bomber is already deleted early (`artlry.cpp:930`). Decision: delayed release stays; B7o changes only who frees. The `S10_STRIKE=1` reload-delta must be run with a round PROVEN created (a log-line count).
- G9 **TG node: prerequisite, transfer semantics, view array, parent pointers.**
  (a) B7o.1 prerequisite: `virtual ~TG_TypeNode()` (`tgl.h:470`). Reconcile with `destroy()`: `TG_TypeNode::destroy()` stays virtual; the base destructor does NOT call a virtual (never from a base destructor); `TG_TypeShape::~TG_TypeShape` keeps its `destroy()` call; the explicit `destroy()` before `delete` at `msl_load.cpp:378` is removed ONLY after the doctest proves the destructor chain runs it once (destroy must be idempotent: `shadowVertexStore` etc. are vectors, so a second call is a no-op). Proof: a doctest with derived-destructor and `destroy()` COUNTS (a `TG_TypeShape` deleted through `TG_TypeNode*` runs `~TG_TypeShape` once and releases its stores once), plus objhash IDENTICAL or the sim pair.
  (b) Transfer and reset semantics (B7o.6a, before the flip): `TG_ShapeRec` assignment deliberately resets animation and cache fields (`tgl.h:451`, `msl_shape.cpp:445`), so a defaulted move is NOT equivalent. Define `TG_ShapeRec::transferFrom(TG_ShapeRec&)` that moves the `node`, applies the same resets the copy assignment applies, and leaves the source with a null node; `Detach` and the compaction loop (`msl_shape.cpp` ~438-481) call it, behaviour identical, proven by a doctest that checks every reset field after a transfer and a compaction.
  (c) View array (B7o.6b): `std::vector<std::unique_ptr<T>>::data()` cannot supply a `T**`. `listOfTypeShapes` (`msl.h:76`) and `listOfShapes` stay RAW view arrays owned by the module (a separate `std::vector<TG_TypeNode*>` refreshed from the owner vector at the single resize/fill point, `msl_load.cpp:84`); consumers (`gos_mech_batcher_flush.cpp:78` etc.) take references, not vector copies, so they are unaffected.
  (d) Parent pointers: nodes hold parent pointers into the shape array; `Detach` and compaction rebuild them after every transfer (a loop over the new array), and a doctest asserts parent validity (each parent points at a live record of the same array) after Detach and after compaction.
- G10 **No saved byte changes.** `Mech3DAppearance::copyTo/copyFrom`, `appearanceTypeID` text and `objTypeNum` are the saved appearance/type state. The `*Data` records in `objmgr_io.cpp:654` are separate structs, not whole live subclasses, and `save_layout_guard.h` pins those records (`:39`): adding a member to `GameObject` is allowed; `sizeof` of every pooled class is printed before and after in the commit. The one exception, the queue record, is handled by G5 (record unchanged, owner elsewhere).
- G11 **Include-only first (F10)** for `<memory>` in `gameobj.h`, objhash-compared. **Forced edits (F11)**: `tools/build_all_targets.py` after every header change; editor and tool edits are listed, never scope.
- G12 **Behaviour that changes goes in the commit and the notes (F12)**: every appearance freed where it was leaked is a named line. No new `STOP`/assert as a check; a malformed state logs one line and continues.
- G13 **Pool buffers: name an owner and a release for EVERY migrated allocation (rev 2, was old B7.5).** Per kind: (a) terrain sub-areas (`short[MAX_SPECIAL_SUB_AREAS]`, 2 per `TerrainObject`, allocated in `init` AND again at 1714/1720; freed at 1094/1100 by `destroy()`): owner `std::unique_ptr<short[]>` members, `reset()` at the existing Free positions, re-alloc paths use `reset(new short[n]())`; (b) weapon-bolt texture text: `std::string` or `unique_ptr<char[]>` member, freed where `Free(textureName)` is today (`weaponbolt.cpp:37`); (c) actor allocation: the `GameObject` operator pair, B7o.9 only; (d) manager pointer arrays: owner `std::vector<GameObjectPtr>` (or the matching typed vectors) members of `GameObjectManager`, with the raw members kept as VIEWS refreshed at every (re)allocation (both `setNumObjects` and the load path in `objmgr_io.cpp`), and `destroy()` gains the explicit release: after the pointee deletion loop it clears the owner vector (today it only nulls the view, relying on `delete objectCache`).
